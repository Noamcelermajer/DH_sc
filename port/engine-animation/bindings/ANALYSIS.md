# Animation channel and value dispatch

This note closes a bounded part of the engine animation runtime from channel registration through sampler lookup and track-specific value dispatch. It does not assign meanings to opaque destination fields or claim a complete animation decoder.

## Provenance

The source is the APK member `lib/armeabi-v7a/libDungeonHunter2.so`, 15,938,284 bytes, SHA-256 `36498eb8180ffb74759e6305e9596db999f18583d460f3b8534abcb6022f5e80`. The exact ARM bodies are in [channel-runtime-functions.asm](reference/channel-runtime-functions.asm); per-function VAs, file offsets, sizes, source listing lines, and SHA-256 values are in [channel-runtime-functions.json](reference/channel-runtime-functions.json). All 28 copied function ranges (4,552 bytes total) were compared byte-for-byte with the APK ELF using its file-backed PT_LOAD mappings. The supplemental [target-binder manifest](reference/target-binder-functions.json) and [ARM excerpt](reference/target-binder-functions.asm) add nine exact function ranges and the relevant `CSceneNodeAnimatorSet` vtable slots; their APK-byte hashes are recorded in the manifest.

## Bounded runtime path

1. `CAnimationSet::compile()` walks animation/channel records and makes virtual calls through the animation-set/template objects. `CAnimationSet::addAnimation(SAnimation const*)` checks the channel type and descriptor fields, including string comparisons, then records the resulting track index. `SAnimationAccessor::getChannel(i)` independently confirms a 16-byte channel-record stride. The exact matching criteria for every special channel code are not reconstructed here.
2. `CAnimationSetTransformationTemplate::addTransformationTargets(CSceneNode*)` creates 16-byte records with channel codes `1`, `5`, and `10`, and stores the supplied scene-node pointer at record offset `+8`; it recursively visits child nodes. The existing [track-selection table](../track_selection.hpp) maps those codes to position-vector3, rotation-quaternion, and scale-vector3 track families. `isAnimationExist()` groups channel codes in its checks, but that routine alone does not resolve every component channel to a destination.
3. `CAnimationSetTransformationTemplate::isAnimationExist()` compares a channel bind string to the names of the seeded nodes and admits matching transform families. `CAnimationSet::compile()`/`addAnimation()` then retain accepted channels. The runtime pointer binder is now traced in [the target-binder manifest](reference/target-binder-functions.json) with exact ARM ranges in [its assembly excerpt](reference/target-binder-functions.asm): `CSceneNodeAnimatorSet` exposes its CAnimationSet through virtual track, bind-URI, and target-count methods. On a changed scene-node bind, `ISceneNodeAnimator::onBind()` stores the node at `+0x10` and calls `forceBind()` when target count is nonzero. For representative track types `1`, `5`, and `10`, `forceBind()` resolves the bind URI from that node via `ISceneNode::getSceneNodeFromUID()`, then calls indexed `setTarget(index, node, nullptr)`. The set stores that pointer in its target array at `+0x28[index]`; `applyAnimationValues()` later consumes the stored pointer with the corresponding track. This closes the template/channel-to-runtime-target-pointer link for the traced route.
4. Separately, the `CSceneNodeAnimator` implementation appends an `SAnimation*` to its 16-byte per-track records. Its `setTarget(index, target, info)` stores the target pointer at record `+4` and retains/replaces the applicator-info reference at `+8`. Runtime compute/apply loops skip records with a null target. Record `+12` is passed by reference through the accessor path; its purpose is not identified.
5. That implementation's `getAnimationData(index)` forms an animation-block search key and calls `CAnimationStreamingManager::getAnimationBlock`; it returns the resolved block data used to form the second word of the local `SAnimationAccessor`. This is the segment/block boundary for that accessor-based path.
6. In that path, `computeAnimationValues()` calls `SAnimationAccessor::getValue`; `applyAnimationValues()` calls `SAnimationAccessor::applyValue`. `SAnimationAccessor::getAnimator()` reads the runtime object pointer at `SAnimation+0x14`. The existing `CAnimationTrackEx` vtable evidence identifies the accessor address-point slots: `+0x68` reaches `getValue(..., int&, bool)`, and `+0x6c` reaches `applyValue(..., int&, bool)`.
7. Both track methods call `findKeyFrameNo`, then test its result together with the caller flag. In `applyValue`, the false branch dispatches through the track object's vtable slot `+0x48` (direct-key wrapper); the true branch uses `+0x40` (interpolated wrapper). The selected position-float3 table resolves those slots to the typed wrappers documented in [the sampler analysis](../ANALYSIS.md). The `getValue` overload has the corresponding direct/interpolated retrieval branches at object slots `+0x28` and `+0x20`.

The `findKeyFrameNoEx<int, 1000>` body reads the sampler's interpolation discriminator and returns interpolation eligibility only when that discriminator is nonzero and the query lies between keys. At this dispatch layer, nonzero values share the interpolation branch; this does not establish that every serialized nonzero enum has the same value-interpolation rule. Typed track vtables select the concrete implementation.

## Sampler and transform metadata

The accessor bodies provide these exact observations:

- Sampler lookups use 28-byte records for time type, interpolation type, time vector, and output vector.
- Channel lookups use 16-byte channel records.
- `hasDefaultValue()` tests `SAnimation+0x18`; `getDefaultValue()` follows that pointer and returns its field at `+8`.
- `getOffsets()` and `getScales()` follow the object at `SAnimation+0x1c` and return its fields at `+8` and `+4`.
- `getOffsetScaleType()` returns `2` when the offset-scale object is absent; otherwise it reads the object's first word. The existing track factory maps absent/2 to float, 0 to character, and 1 to short-integer templates.
- The transformation template's `getDefaultValue(channel, out)` scans its stored records through a helper and returns a found/not-found result. This trace does not prove the default-value payload layout or every default fallback rule.

The selected float3 position sampler has a concrete adjacent-key linear implementation in [value_sampling.hpp](../value_sampling.hpp). The [typed-track analysis](../typed-tracks/ANALYSIS.md) additionally proves float quaternion and scale-vector3 direct/interpolated paths. Other float/integer variants, byte/short tracks, component tracks, and quaternion-angle interpolation remain open.

## Boundary and unresolved behavior

The engine evidence establishes how animation data reaches the `CAnimationTrackEx` dispatch, how transform-template target records are seeded, and how the compiled track's bind URI becomes a stored scene-node pointer on the traced `CSceneNodeAnimatorSet` path. The position-track target slot resolves to `ISceneNode::setPosition(vector3d<float> const&)` when its target is a `CSceneNode`; see the [focused target trace](../targets/ANALYSIS.md). These traces do not establish the serialized meaning of every BRES field, every callback-produced channel binding, all `void*` target types, the meaning of record `+12`, or all default/offset-scale transformations. They also do not establish broader coordinate-space semantics. No tests or builds were run.
