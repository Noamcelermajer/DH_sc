# Native audio transition-rule rows: parser to runtime consumers

## Result

This audit connects the serialized `Rule` chunk to the engine decoder's
`TransitionRule` consumers. The parser copies each row into a runtime table;
the parser-derived stride and the runtime's table indexing both resolve to 36
bytes in the supplied assets. Selected runtime methods give direct meanings to
most row words as branch inputs, cached values, or progress-calculation inputs.
The binary does not provide semantic field names or units, so the offsets below
remain the authoritative labels.

This is the `vox::` audio engine decoder inside the APK's native library. It
does not cover game-side sound selection, music policy, or event-to-audio
mapping.

## Parsing and row layout

`vox::DecoderNativeCursor::ParseFile()` (VA `0x008738bc`, size `0xa38`, SHA-256
`db37531fce39bdf9c8d2a98084ddb31360fb81ddae015d34a1474f5d9b294674`) compares
the chunk tag with `Rule` and branches to its handler. That handler reads the
leading row count, derives a row stride from `(payload_length - 4) / count`,
constructs transition-rule storage, and copies each source row using that
derived stride. The destination advances by `0x24` bytes per row. In the
observed corpus the derived stride is also `0x24`, so each 36-byte serialized
row is copied intact into the runtime table. The parser does not assign names
to the copied words, and its division path does not prove a general malformed
input contract.

`UpdateSegmentsStates()` (VA `0x00885740`, size `0x244`) and
`InterpretTransitionRule(int)` (VA `0x00885984`, size `0xb8`) independently
select rows using `index * 0x24`. Together with the parser copy, this ties
serialized row offsets to runtime `TransitionRule` offsets without relying on
an assumed C++ layout.

### Runtime-observed fields

| Serialized row offset | Directly observed use in the engine | Boundary |
| --- | --- | --- |
| `+0x00` | `ApplyTransitionRule` compares the word with `1`, uses that branch in its state logic, and copies the word to decoder state at `+0x7c`. | A discriminator-like input; no public enum name is recovered. |
| `+0x04` | `InterpretTransitionRule` checks zero before its playlist-lookup path. `IsExtraSegmentNeeded` returns true for a nonzero word when its transition-count gate and non-null rule path are active. | A branch/gate word by observed control flow; no symbolic name is assigned. |
| `+0x08` | `ApplyTransitionRule` copies the word to decoder state at `+0x80`. | Cached value only; its semantic name is unknown. |
| `+0x0c` | `UpdateOldSegmentState` copies this word to decoder state at `+0xfc` and branches when it equals `1`. | Selector-like input; other values and meanings are not established by this corpus. |
| `+0x10` | Read by `UpdateCurrentSegmentState` and passed through the rate/progress arithmetic that updates current-segment state. | Numeric role and unit remain unknown. |
| `+0x14` | Also read by `UpdateCurrentSegmentState` and combined with the rate/progress calculation. | Numeric role and unit remain unknown. |
| `+0x18` | Read by `IsExtraSegmentNeeded`, which compares it as a float against zero when `+0x04` is zero. Also consumed by old- and dying-segment progression. | Float-like use is supported by the call to `__aeabi_fcmpgt` and the arithmetic path; units are unknown. |
| `+0x1c` | Read by `UpdateOldSegmentState` in its progression arithmetic with the decoder's rate-derived value. | Numeric role and unit remain unknown. |
| `+0x20` | No semantic use is established by the selected consumer ranges in this audit. | All corpus rows contain `0xffffffff`; this invariant does not reveal its meaning. |

The runtime symbols and hashes for those observations are listed in
[`functions.json`](functions.json). The field accesses and branch outcomes can
be checked in the exact listings named there.

## Corpus results

[`corpus/rule-rows.json`](corpus/rule-rows.json) is generated by the read-only
[`census_transition_rules.py`](tools/census_transition_rules.py) scan. It reads
the 12 cached `.vxn` files, checks the parser-derived chunk window and record
bounds, then records each `Rule` body, file hash, row offset, raw bytes, and
nine little-endian words. Results:

- 12 files and 23 rows; all `Rule` bodies have count-derived 36-byte rows.
- The 11 level files each contain two byte-identical rows: 22 rows total with
  words `[1, 0, 0, 0, 0x40000000, 0x40000000, 0x40000000, 0, 0xffffffff]`.
- `m_title.vxn` contains one row with words
  `[0, 6, 0, 0, 0, 0, 0, 0, 0xffffffff]`.
- Thus the corpus has two raw row patterns. The `0x40000000` words are the
  binary32 encoding of `2.0`; the runtime's float comparison establishes a
  float interpretation for `+0x18` on that path. The other numeric fields
  remain raw where their type is not established.
- Example level file: `m_level_cathedral_sfx_catacomb.vxn`, SHA-256
  `6c0236d19b66011d986a7fd31a332257d8f689ceea69e049abf90376d33ed909`; its
  Rule payload SHA-256 is
  `199f5bae542f4a63d8d7be090f1452537db9897cfba406cfd5399b2d7c738521`.
- Title file: `m_title.vxn`, SHA-256
  `6dcd53d955ab1c923ea0bb951ce9c5d21dbf086d64d43314002ebfe2c2cd6f4f`; its
  Rule payload SHA-256 is
  `36ab377077031b9b6d09b6424000ca06c33f281d9ff3751eb82279dc88525143`.

The 12 files are the recovered cache corpus only. Their filenames and
presence do not prove which game-side requests load them or which transitions
execute at runtime.

## Remaining limits

This maps parser-to-runtime row copying and direct uses of offsets `+0x00`
through `+0x1c` in selected engine methods. It does not establish public field
names, complete semantics for branch values, units or transition timing,
`+0x20` meaning, malformed-file behavior, or runtime execution for every row.
The title row's differing values demonstrate a second serialized pattern, not
that a specific title transition occurred. No audio playback comparison,
build, or test was run for this audit.
