# GLES vertex and index buffer path

This note follows engine-owned `IBuffer` objects into GLES2 vertex setup and mesh draw submission. It is static analysis of the supplied ARM32 library. The exact APK identity, ELF load map, range hashes, aliases, and copied instructions are in [`original-functions.json`](original-functions.json) and [`reference/original-functions.asm`](reference/original-functions.asm).

## Buffer object lifecycle

`CCommonGLDriver::createBuffer` (`0x005b13f4`, 140 bytes) allocates a 32-byte object, delegates its common fields to `CBufferBase` (`0x006ddf84`, 108 bytes), installs the GL-buffer vtable, and initializes the intrusive reference count. `CBufferBase` calls `IBuffer` construction (`0x005a1908`, 116 bytes). The instructions show an in-memory object with CPU-data pointer at `+0x8`, byte size at `+0xc`, type and usage bytes at `+0x10/+0x11`, state bytes at `+0x12/+0x13`, driver pointer at `+0x14`, GL name at `+0x18`, and a zero-initialized cache field at `+0x1c`. These are runtime offsets, not recovered serialized fields.

The GL name is created lazily. `CBuffer::bindImpl` (`0x005b67b0`, 528 bytes) selects whether the buffer type can use a GL target, calls `glGenBuffers`, binds the selected target, and uploads with `glBufferData`. The type and usage tables are indexed by the runtime enum bytes; this note does not assign names to enum values. `CBuffer::update` (`0x005b6374`, 332 bytes) uses `glBufferData` for the full dirty upload and `glBufferSubData` for the other update branch. The upload path checks `glGetError`; the shown failure branch deletes and clears the generated name and updates the state byte.

`IBuffer::map` (`0x005a19f0`, 204 bytes) tracks nested map state and dispatches through the object's map hooks when required. `CBuffer::mapImpl` (`0x005b3a1c`, 224 bytes) returns the CPU backing pointer in its mapped-data branches; the inspected body contains no GLES buffer-map call. `IBuffer::reset` (`0x005a1cb4`, 360 bytes) can replace or clear the pointer/size and updates state bits. On the path with its internal ownership bit set, it calls array delete for the old CPU pointer. The bit meanings and ownership rules at callers remain unknown.

`CBuffer::unmapImpl` (`0x005b2468`, 96 bytes) restores buffer-binding state and clears a mapped-state byte. `CBuffer::~CBuffer` (`0x005b24c8`, 116 bytes) calls unmap when its mapped-state bit is set, calls `unbindImpl` when its GL-name state bit is set, then destroys its `IBuffer` base. `unbindImpl` (`0x005b051c`, 120 bytes) calls `glDeleteBuffers`, clears a matching driver cache entry and clears the stored name. This bounds object-local GL cleanup; it does not establish which outer resource or scene owns the last reference, GL-context shutdown ordering, or every error and device-loss path.

## Vertex layout and draw path

`CVertexStreams::setupStreams` has two observed forms: a backing-buffer plus attribute-mask form (`0x005a15c0`, 460 bytes) and a `SVertexStreamData` record form (`0x005a178c`, 236 bytes). The first assigns references to a shared `IBuffer` and computes per-stream offsets. The second accepts 16-byte source records and adjusts intrusive references. Their layouts differ from the destination `SVertexStream` records: source `SVertexStreamData` contains an `IBuffer*` at `+0`, byte offset at `+4`, scalar/value-type enum at `+8`, component count at `+12`, and stride at `+14`. The copy routine places these at runtime record offsets `+0`, `+4`, `+10`, `+12`, and `+14`; it preserves the destination record's engine attribute code at `+8`. `CVertexStreams` construction assigns that code from the sparse attribute mask (or an explicit stream record), as traced in the [producer audit](../../engine-shaders/attributes/producer-stream-audit/ANALYSIS.md).

`setupArrays` (`0x005b6584`, 484 bytes) walks reflected shader attributes, maps each engine code through the material's 30-byte stream map to a runtime stream ordinal, then consumes the selected 16-byte `SVertexStream` record. It binds the buffer at `+0`, adds byte offset `+4`, and passes the scalar-type enum at `+0x0a`, component count at `+0x0c`, and stride at `+0x0e` to `glVertexAttribPointer`; the runtime record's `+8` code is not directly read by this helper. The scalar enum is translated through an engine table whose entries are not reproduced here. Enabled attribute arrays are updated from the shader attribute map.

For each attribute, `setupArrays` calls `CCommonGLDriver::setBuffer` (`0x005b6514`, 112 bytes), which first checks `updateBinding` (`0x005b64c0`, 84 bytes). The driver caches bindings by buffer type. The observed usage enum value `4` returns the CPU data pointer; the other branch returns null while using the GL name, so the vertex pointer passed to GLES is either CPU base plus stream offset or a buffer-relative offset. The numeric enum is recorded without assigning a source-level name.

`IVideoDriver::drawMeshBuffer` (`0x0035ebd0`, 96 bytes) forwards the mesh buffer's vertex and primitive streams through the driver's virtual draw slot. The mesh-buffer draw overload (`0x005adfa8`, 56 bytes) dispatches through the driver's `drawImpl` slot, with a batching branch when the corresponding driver flag is set. `CCommonGLDriver::drawImpl` (`0x005b8bc8`, 448 bytes) binds the `CPrimitiveStream` buffer through `setBuffer`, commits per-pass parameters, calls `setupArrays`, and then calls `drawPrimitives` (`0x005b09c8`, 212 bytes). The indexed branch calls `glDrawElements` with the binding result plus the stored byte offset, a count from the primitive stream, and table-selected GL mode/type values. The unindexed branch calls `glDrawArrays`. The exact serialized representation that creates these runtime records is outside these ranges.

## Evidence boundary

This checkpoint establishes the GLES buffer object calls, map/reset/update/delete behavior, runtime vertex-layout fields, and the mesh-to-driver-to-GLES submission path. It does not recover material shader meanings, all sources that populate the buffers, the scalar-enum-to-GLES table, all serialized meanings of `SBufferConfig`/`SVertexStreamData`/`CPrimitiveStream`, caller ownership and lifetime rules, or context/thread policy. Treat enum values, state bits, and offsets as observed runtime evidence; do not treat them as a complete file-format schema.

No tests or builds were run.
