# Selector-4 light attachments and partial `SLight` payload

## Finding

The engine's selector-4 attachment route resolves a light name from an instance record, looks for that name in the current Collada data root, and constructs a Collada light scene node when a matching `SLight` row is found. APK-matched ARM code establishes the lookup row stride and the constructor's selected input fields. It does not establish a complete serialized light schema or safe record bounds.

The recovered application supplies a concrete `ColladaFactory` object to the scene path, but the light virtual slot in that object's vtable contains the engine's base `CColladaFactory::createLight` target (`0x00631af8`). The `SceneManager` factory registration itself is app-side context recorded in the neighboring [attachment factory audit](../attachment-factory-audit/ANALYSIS.md); the lookup, factory implementation, and `CLightSceneNode` constructor analyzed here are engine-side code.

## Selector-4 route

`CColladaDatabase::constructNode`, VA `0x0061b2f4`, has the attachment switch and is already indexed in [serialization-ranges.json](../serialization-ranges.json) with exact APK bytes. Its selector-4 arm at `0x0061b664` loads the attachment's second word as an instance pointer, loads the instance's word at `+0x04`, adds one, then calls `CColladaDatabase::constructLight(char const*, CRootSceneNode*)` at `0x0061b24c`. That overload calls `getLight(char const*)` at `0x0061b1ec`, then delegates the resulting pointer to `constructLight(SLight*, root)` at `0x00619404`.

The name lookup reads the light-table count at data-root `+0x44` and table base at `+0x48`. It compares the first word of each candidate row with the requested name and advances by `0x18` bytes. `getLight(int)` at `0x0060e3ac` independently indexes the same table with the same stride. For a non-null `SLight*`, `constructLight` reads the database's factory pointer at `+0x04`, invokes the factory virtual at vptr `+0x0c`, and passes the light record. The concrete app `ColladaFactory` slot is at vtable-start `+0x14` (vptr address point `+0x0c`) and its APK word is `0x00631af8`. The engine implementation allocates `0x16c` bytes and calls the Collada `CLightSceneNode` constructor at `0x006444ec`; a returned node is added to the supplied root.

The dispatch slice and all six new complete function ranges are copied in [light-payload-excerpts.asm](reference/light-payload-excerpts.asm). Their hashes and ELF offsets are in [function-manifest.json](function-manifest.json). The linked `constructNode` range/hash points to the existing scene serialization manifest. All copied ARM rows were compared byte-for-byte with the APK ELF.

## Fields consumed by the runtime constructor

`CLightSceneNode::CLightSceneNode(CColladaDatabase const&, SLight&)` loads these input offsets from its `SLight&`:

| `SLight` offset | Observed engine use | Boundary |
| --- | --- | --- |
| `+0x08` | Numeric branch selector; values 0–3 select separate initialization blocks. The blocks write runtime-light type words 3, 0, 1, and 2 respectively at runtime light `+0x58`. | These are observed numeric mappings only. No symbolic type names are assigned. Values greater than 3 take the default block, whose full meaning is unresolved. |
| `+0x0c..+0x0f` | Four individual bytes passed through conversion helpers along with the word at `+0x10`; converted words are stored in the runtime light's color-data region. | Channel names, color-space behavior, and normalization details are not established here. |
| `+0x10` | Loaded as a 32-bit word and passed through a conversion helper that also feeds the four byte conversions. | A sample contains bits `0x3f800000`; the complete source type and numeric role are not proven by the constructor alone. |
| `+0x14` | For numeric input types 1 and 3, treated as a pointer to five contiguous 32-bit words. The constructor copies those words to runtime-light offsets `+0x34`, `+0x38`, `+0x3c`, `+0x48`, and `+0x4c`. | Input types 0 and 2 do not take this five-word path. The meanings and units of the words are unknown. |

The code also places the resulting runtime light data inside the scene-node object and initializes its parent/reference state. Those object-management writes are not serialized `SLight` fields.

## BDAE corpus evidence

The read-only [light corpus](light-corpus.json) was generated by [catalog_light_payloads.py](tools/catalog_light_payloads.py). It scanned 2,901 cached BDAE files, followed the selected type-6 visual-scene path, walked the proven `0x50`-stride nodes and 8-byte attachment rows, then used the selector-4 name adjustment and the engine-visible `0x18` light-row stride. Fixup-marked pointers and complete table spans were checked before following each relevant field.

The scan found 182 active selector-4 attachments. Forty-five match a light row in the same BDAE: 42 use numeric type word 0 and three use type word 1. The other 137 all request `ambient-environment-light`, but their own root light-table count is zero. This is only a within-file corpus result. It cannot say whether the live loader has merged another library into the queried data root or whether those lookups return null.

Two matching samples illustrate the limits and useful field evidence:

| Sample | `SLight` row and observed values |
| --- | --- |
| `data/3d/interface/enemy_summon.bdae`, SHA-256 `900e0aaf312fbc3c27a37a8e2c08a50912cc0fa0a8aa0c8fb1b758afda4fcddb` | Row `0x5e0c` is found through root count field `0x20d4` and fixup pointer field `0x20d8`. It has type word `0`, bytes `[40, 40, 40, 255]` at `+0x0c`, word `0x3f800000` at `+0x10`, and null word at `+0x14`. |
| `data/3d/light/common_light.bdae`, SHA-256 `38c74814714673f7a4104bddf6b28ba059a2f71e3654b7de09da28a35d8997b3` | Selector-4 attachment name `Omni01-light` matches row `0x2b4` (table count 2 at `0x20c`; fixup table pointer at `0x210`). It has type word `1`, bytes `[249, 196, 114, 255]` at `+0x0c`, word `0x3f800000` at `+0x10`, and a fixup pointer at `+0x14` to `0x2e4`. The 20 bytes there are five raw words: `[0x3f800000, 0, 0, 0x120, 0x138]`, the same five-word sequence consumed by the constructor's type-1 path. |

Across all light-table rows in the recovered corpus, only input type words 0 and 1 occur (42 and 3 rows). Types 2 and 3 are handled in the engine constructor but have no example in this cache. These observations identify a path and partial field use; they do not demonstrate runtime behavior for every attachment or produce a general-purpose BRES parser.

## Verification and remaining boundary

The source APK SHA-256 is `32c2d027b585a42547311cd95da6a3975fdb3174e663e513d42a7f49d1a4c200`; its ARM ELF member SHA-256 is `36498eb8180ffb74759e6305e9596db999f18583d460f3b8534abcb6022f5e80`. The six new function ranges total 988 bytes and map through PT_LOAD segment 1 at same-numbered file offsets. The concrete factory vtable word is separately hashed through segment 2. The corpus assets are identified by their individual hashes above and in the JSON.

The unresolved pieces are the semantic names/types of numeric light fields, the complete `SLight` and instance record extents, bounds validation in the original runtime path, the table-merging or null-lookup behavior for the 137 references without a local table, and values/types 2–3 in an actual asset. No parser or replacement engine implementation is claimed by this note.
