# Native image-loader and decoder matrix

## Binary identity and scope

This map uses `lib/armeabi-v7a/libDungeonHunter2.so` from `Dungeon-Hunter-2-HD-v1-0-2.apk`. The verified APK SHA-256 is `32c2d027b585a42547311cd95da6a3975fdb3174e663e513d42a7f49d1a4c200`; the ELF SHA-256 is `36498eb8180ffb74759e6305e9596db999f18583d460f3b8534abcb6022f5e80`. The executable `PT_LOAD` has `p_vaddr=0`, `p_offset=0`, and `p_filesz=0x955130`, so every in-range ELF VA below also gives its file offset. The APK and extracted ELF hashes were checked in this pass. Existing per-function manifests and ARM listings are linked in each row; hashes cover the exact stated byte range.

“Engine” below means the Glitch/GameLoft loader and pixel-format code in this ELF. libjpeg, libpng, and zlib are support implementations embedded in the same ELF. A format name or loader entrypoint alone does not prove that an engine path performs software decompression.

## Shared dispatch contract

`CTextureManager` registers loaders in this exact order: **BMP, JPG, TGA, ATC, PNG, DDS, PVR**. `getImageLoader` calls every registered loader's content probe in that order, saves and restores the `IReadFile` cursor around each probe, and returns the first positive match. Only after every content probe fails does it try extension predicates in registration order. The exact ranges are:

The manager sends ATC, DDS, and PVR through `loadTextureHeader` → texture creation → `loadTextureData`. The other four use `loadImage` and the image-to-texture path. ATC and DDS also have callable `loadImage` entrypoints, but the manager's true interface overrides route them through the direct texture path. The common data transfer and renderer upload path are mapped in [`loaders/ANALYSIS.md`](loaders/ANALYSIS.md); it stores compressed payloads in texture backing and selects compressed GLES uploads when the pixel-format row requests them. That establishes an engine transfer route, not extension availability or successful rendering on a particular device.

## JPEG support-library boundary

The engine wrapper calls these named libjpeg routines directly from `CImageLoaderJPG::loadImage`. They are defined in `.text` of the same ELF, with no dynamic JPEG import; they are bundled support code, not Glitch loader policy. The call sequence is `jpeg_std_error` → `jpeg_CreateDecompress` → `jpeg_read_header` → `jpeg_start_decompress` → repeated `jpeg_read_scanlines` → `jpeg_finish_decompress` → `jpeg_destroy_decompress`.

The engine's input-source/error bridge is also local code: `init_source` at `0x00604adc + 0x04`, `fill_input_buffer` at `0x00604ae0 + 0x08`, `skip_input_data` at `0x00604ae8 + 0x20`, `term_source` at `0x00604b08 + 0x04`, `output_message` at `0x00604ed8 + 0x70`, and `error_exit` at `0x00604f48 + 0x24`. Their functions are inside the hashed JPG-loader region and symbols are present in the recovered symbol table; `loadImage` installs these source-manager and error callbacks around the embedded codec.

## Most grounded implementation gaps

The principal game-texture path supported by the corpus is BTEX/PVR: 234 recovered wrappers and 3,437 BRES image-record rows joining to 178 distinct files. Header parsing and PVRTC decode are partly reconstructed, but full generic pixel conversion, capability choice, and target GLES behavior are not. Finish that transfer/conversion boundary before spending effort on formats with no observed payloads.

A concrete separate decoder slice is the engine PNG-to-`CImage` adapter. It is mapped precisely and the recovered tree has 121 valid PNG resources, but there is no source port for the engine wrapper. Reusing a host PNG library and reproducing the mapped transforms, output format selection, row layout, and error cleanup would cover that engine handler without rewriting libpng. Its value for game-texture rendering is uncertain: these files are under `files/res`, and no BRES image path refers to them. The eight cache TGA32 files already have a bounded implementation. BMP, JPEG, ATC, and DDS have native handlers, but this cache has no matching payload bytes for them.

## Limits

This is a static dispatch and cache map. It does not prove that any particular resource passed through `CTextureManager` in a live session, that the manager's Android file route could open it, or that the GLES driver accepted a compressed format. The cache scan covers the recorded 5,839-file `files/**` extraction, not arbitrary runtime/downloaded resources. PVR conversion branch choice, all malformed-input handling, full TGA/BMP behavior, and PNG/JPEG output on device remain unverified. No builds or tests were run.
